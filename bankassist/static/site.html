Six languages

Not a translation layer.

Every one of these has its own complete table of what the assistant says, its own detection rules, and — the part that matters — its own safety rules, written and tested in that language. A customer trying to talk the assistant into revealing an account detail does not phrase it in Amharic the way an English phrasebook would translate it. So the guardrail is not translated. It is written per language, and there is a test for each one.

What it will not do

The section your risk officer reads first.

An assistant that occasionally invents an interest rate is not a cheaper contact centre — it is a regulatory incident with a chat interface. These are enforced in code and checked by the test suite on every change, not written into a prompt and hoped for.

01

Answers come from your documents, with the source attached

Every substantive answer carries the passage it came from. If your knowledge base does not cover the question, the assistant says so and offers a person — it does not improvise a plausible answer.

02

It cannot invent a rate, a fee, or a balance

Figures come from retrieved content or from a tool, never from the model's own memory. This is a rule the code enforces, and the evaluation suite runs against a fixed set of questions before any knowledge-base or model change ships.

03

It refuses anything that needs account access — and is tested for over-refusing too

Balances, PINs, card blocks and transfers are out of bounds without an authenticated session. The guardrail is checked in both directions, because an assistant that refuses "what documents do I need to open an account?" has failed just as surely as one that leaks a balance.

04

Education, not advice

It will explain how a product works. It will not tell a customer which one to buy. That line is written into the contract as well as the code.

05

One institution's data cannot reach another's

Every query touching tenant data is scoped by institution, and an integration test asserts it. Knowledge bases are strictly isolated; nothing is pooled across customers.

06

Every action is auditable

Staff actions are written to an audit log with actor, action and entity. Administrator accounts carry a second factor.

When it must not answer

A real person, inside the same conversation.

The assistant hands over to a teller without the customer starting again. The transcript, the detected language and the reason for the escalation are already on the teller's screen when they pick it up — and the customer stays in the channel they were already using, with a live voice call if the conversation needs one.

Routed by expertise

Data residency

Built to run inside Ethiopia.

Chat content is personal data whether or not it is linked to an account, so the deployment target is in-country infrastructure rather than a foreign region with a data-processing addendum attached. Olink Technologies has been through in-country certification before with Onekof, and that playbook is what this product follows.

⌂

Your knowledge base stays yours

Documents you load are used to answer your customers. They are not pooled, not used to train a shared model, and not shared between institutions.

✎

Chat text is not logged

Message content is not written to application logs. What is recorded is what the system did — intent, language, outcome — which is what the reports are built from.

Pricing

Per institution. Never per seat.

Charging per agent seat punishes you for putting the assistant in front of more customers, which is the entire point of buying it. So the model is a one-time setup fee plus a monthly subscription tiered by conversation volume — the same shape the established platforms in this category use, because it is the shape a bank's procurement team can actually approve.
